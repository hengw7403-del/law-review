# 设计文档

本文件记录系统的架构决策及其理由。读者应已了解项目做什么（见 [README](../README.md)）。

设计文档不是为了证明"想得周全"，而是记录**当时为什么这样选、放弃了什么**——这些问题在半年后会重新出现。

---

## 一、系统架构

### 组件

```
┌──────────┐     HTTP      ┌──────────┐
│ 浏览器    │ ────────────→ │  nginx    │
└──────────┘               └────┬─────┘
                                │ 反代
                           ┌────▼─────┐
                           │   api    │  FastAPI
                           │          │  · 认证 / 权限
                           │          │  · 上传 / 解析
                           │          │  · 建审查任务
                           └────┬─────┘
                                │ 读写
                     ┌──────────▼──────────┐
                     │      SQLite          │
                     │  contracts/clauses   │
                     │  review_tasks/items  │
                     │  knowledge_chunks    │
                     └──────────▲──────────┘
                                │ 轮询领任务
                           ┌────┴─────┐
                           │  worker  │  独立进程
                           │          │  · 检索
                           │          │  · 调模型
                           │          │  · 校验落库
                           └──────────┘
```

**api 和 worker 为什么分开：**

一次审查要调几十次模型，单次 3–5 秒，总计几分钟。如果放在 HTTP 请求里：
- 请求会超时
- 用户刷新页面就断
- 没办法重试单个失败项

拆成独立进程后，HTTP 只负责"创建任务"，浏览器轮询进度。任务生命周期和请求生命周期解耦。

### 一次审查的时序

```
1. 用户点「发起审查」
2. api 建任务（status=queued），生成检查计划，立即返回 task_id
3. 浏览器开始每 2 秒轮询 GET /tasks/{id}
4. worker 领到任务（queued → running），预建 review_items（全部 pending）
5. 逐单元执行：
     a. 检索知识库（BM25，Top-5）
     b. 组装提示词，调模型
     c. 四层校验模型返回的依据
     d. 短事务写结果并提交，再用独立短事务更新 done_items
6. 全部完成：有失败 → partial_failed，无失败 → completed
7. 浏览器看到终态，停止轮询
```

**为什么每个单元单独提交事务**：第 5 步要花 3–5 秒，如果攒到最后统一提交，中途崩溃会丢掉全部结果。逐个提交的代价是更多 I/O，换来的是"崩了不重跑已完成的单元"。

## 二、数据模型

七张表，关系如下：

```
users ──┬─→ contracts.owner_id
        └─→ contracts.reviewer_id

contracts ──→ clauses（1:N，parent_clause_id 自引用表达条款层级）
          └─→ review_tasks（1:N，按 review_version 递增）

review_tasks ──→ review_items（1:N）

knowledge_chunks ──→ （独立，检索时按 enabled 过滤）

llm_logs ──→ review_tasks / review_items（记录每次调用）
```

### 几个字段的用意

**`clauses.char_start` / `char_end`**

条款在合同原文中的**字符偏移**，不是字节偏移，不是段落号。

用途：报告里点击条款能定位到原文。这是"审查结果可信"的一部分——用户要能一键看到上下文，而不是自己去翻。

**`review_items.item_key`**

形如 `clause:<clause_id>:<rule_id>` 或 `contract:<rule_id>`，唯一约束。

用途：幂等。worker 重跑时靠它判断"这个单元处理过没有"，不会重复扣费。

**`review_items.check_status`**

六种取值：`pending` / `supported` / `insufficient` / `no_issue_detected` / `not_applicable` / `failed`。

**不是三态的原因见决策 3。**

**`review_tasks.input_snapshot`**

任务创建时冻结的合同快照。

用途：报告可复现。用户改了合同，旧任务的结果仍然对应旧的输入。

**`knowledge_chunks.verified` / `enabled` / `superseded`**

三个独立标记：
- `verified`：人工核对过原文
- `enabled`：在检索范围内
- `superseded`：被新版本取代

**为什么不用一个 `status` 字段**：核对和启用是两个动作，可能"核对过但暂不启用"，也可能"启用着但发现有问题要停用"。三个布尔值比一个枚举表达得更准。

## 三、关键设计决策

### 决策 1：BM25，不做向量检索

**背景**：法条检索需要"找到相关条文"。可选 BM25（词频）或向量（语义）。

**备选**：
- BM25：快、可解释、零额外依赖、结果可复现
- 向量：能理解同义表达，但需要 embedding 模型 + 向量库 + 每次查询一次 API 调用

**决策**：BM25。

**理由**：

法条检索有个特殊之处——**法律术语高度规范**。"违约金"、"解除"、"不可抗力"这些词在合同和法条里用法一致，词面匹配的召回率比一般文本高得多。实测中「违约金过高怎么办」能直接命中第 585 条，分数 3.851，断层到第二名 0.135。

**代价（必须承认）**：

BM25 不通语义。实测中「合同怎么解除」的查询，第 563 条排第四——因为它和查询共享的词少，但语义上高度相关。

**这不是可以被忽略的缺陷**，是二期要补的。在补齐之前，系统对"用不同措辞表达同一概念"的召回是不完整的。

**为什么现在还不上向量**：向量检索要引入 embedding 模型、向量索引、以及每次查询的 API 成本。在规则覆盖本身还没验证完的阶段，加这个只会让问题更难定位。

---

### 决策 2：依据必须从候选集里选，服务端校验四层

**背景**：模型会编造法条。

这不是假设——LLM 在法务场景编造条文号、改写条文内容是常见失败模式。如果报告里出现一条不存在的法条，整个系统的可信度归零。

**决策**：四层校验，任何一层不过就降级。

```
第 1 层  模型只能从本次检索结果（candidate_ids）里选
第 2 层  服务端校验返回的 ID 是否都在候选集内，不在的直接丢弃
第 3 层  引文由服务端从数据库读取，不采用模型返回的引文文本
第 4 层  校验后无有效依据 → 降级为 insufficient，不硬凑结论
```

**关键点**：第 3 层——**引文永远从数据库取**。模型只负责说"我引用第几条"，条文内容一个字都不采信模型的。

**实测验证**：用一个假 ID 让模型返回，四层校验全部拒绝，最终降级为 `insufficient`。

**代价**：

模型偶尔会返回空 `evidence_ids`（即使候选里有合适的条文）。这时系统会判 `insufficient`——**看起来像"没查到"，实际是"模型没用上"**。

这是安全性和可用性的取舍：宁可显示"依据不足，请人工核查"，也不能显示一条编造的法条。

---

### 决策 3：四态，不是三态

**背景**：最初设计是"有问题 / 没问题 / 查不了"。

**问题**：这个分类把两件不同的事混在一起。

- 「查了，条款没问题」——用户不用管
- 「查了，但知识库里没依据」——用户要人工补查
- 「这条根本不涉及这个规则」——用户不用管

三者对用户的含义完全不同。

**决策**：四态 + 一个"不适用"。

| 状态 | 含义 | 用户该做什么 |
|---|---|---|
| `supported` | 发现风险，且有依据 | 逐条看 |
| `insufficient` | 疑似有问题，但没依据 | 人工核查 |
| `no_issue_detected` | 查了，没问题 | 不用管 |
| `not_applicable` | 规则不适用于本条款 | 不用管 |

**为什么值得多一个状态**：

报告统计表里，「未发现问题」和「依据不足」必须分列。合并会误导——用户看到一个"未发现问题：8"，会以为都没事，其实里面有 3 条是"没敢下结论"。

**代价**：状态多了，前端展示和统计都复杂了。但这是必要的复杂度。

---

### 决策 4：条款级和合同级检查分离

**背景**：第一版把两件事混在一起查，结果很糟。

**现象**：

扩规则到 10 个后，一次全量审查产生 19 个 `insufficient`。查下来是同一个原因——

> 第八条保密条款的判定理由：「缺少独立违约金、期限」

但违约金在第十条明明有约定。**条款级检查只看自己，不知道合同别处有安排**，于是到处报"缺这个"，然后找不到依据就降级。

**决策**：划清职责。

```
条款级  →  只看本条款写了什么、写得对不对、对我是否不利
合同级  →  只看合同整体缺什么，不评价单个条款
```

条款级提示词里明确禁止：

```text
禁止以"本条款缺少某内容"为由报风险。
本条款内容正常就判 no_issue_detected。
不要因为"缺了某个约定"降级为 insufficient。
```

**效果**：`insufficient` 从 19 降回 0。

**这条决策的教训**：两个检查混在一起，不是"顺便都能查"，而是**互相干扰**。分开之后各自更准，成本还更低。

---

### 决策 5：确定性流程，不用 Function Calling

**背景**：有了工具调用能力后，直觉是让模型自己决定"先查法规再判断"。

**备选**：
- Function Calling：模型自主决定调用顺序和次数
- 确定性流程：代码固定「检索 → 判定 → 校验」三步

**决策**：确定性流程。

**理由**：

1. **可复现**：同一个条款，两次运行走同一条路径。Function Calling 每次可能不一样，出问题难定位。
2. **可控成本**：一个单元固定 1 次调用。自主调用可能 1 次也可能 5 次，预算不可控。
3. **任务本身是确定的**：审查合同就是"每条查一遍"，没有需要模型自己规划的部分。

**代价**：如果以后要支持"复杂条款需要多轮检索"（比如一次查不相关就换个说法再查），确定性流程就限制了。到时候可能要引入受限的自主性。

---

### 决策 6：SQLite，不是 PostgreSQL

**背景**：法律场景的名字容易让人以为数据量很大。实际上：一个法务一年审 200 份合同，每份 20 条，5 年不到 2 万条。

**决策**：SQLite。

**理由**：
- 单文件，备份就是复制一个文件
- 无需运维，Docker 里挂一个目录就完事
- 支持事务、外键、并发读

**代价**：
- 写并发差（同一时刻只有一个写者）
- 不适合多实例部署

**这不是"不够用"，是"当前场景够用"**。如果要多租户、多实例，换 PostgreSQL 是必须的——但那是另一个产品阶段的事。

**迁移成本可控**：所有访问都走 SQLAlchemy ORM，换数据库主要是改连接串和少量方言相关的 SQL。

---

### 决策 7：字符偏移按 code point，不是 UTF-16

**背景**：条款切分后要记录位置，用于报告点击定位。

**陷阱**：Python 字符串索引是 code point，JavaScript 是 UTF-16。合同里出现 emoji 或生僻字（如 `𠮷`），两者的下标就会错位。

**现象**：前端按 UTF-16 下标去截原文，切出来的文字会错位一两个字——**点击定位就废了**。

**决策**：数据库存 code point 偏移，前端也按 code point 计算（`Array.from(str).length`）。

**验证**：合同 A 12 条、合同 B 10 条，共 22 条 offsets 与原文严格比对，零偏差。

---

### 决策 8：规则带适用条件

**背景**：一开始每个条款都要跑每个规则。12 条 × 10 规则 = 120 个单元。

**问题**：大量单元是"用错的规则查错的条款"。服务条款用「违约责任」规则查，模型只能回 `not_applicable`——浪费时间、浪费钱、还制造噪音。

**决策**：每个规则定义关键词，条款不命中就不生成检查单元。

**数据**：120 个单元 → 实际只调模型 44 次。

**代价（真实踩过的坑）**：

第一版关键词表只有「违约」，漏了「违反」。第十一条原文写的是：

> 一方严重**违反**保密、付款或交付义务…

一个字之差，整条被跳过，**而这条里藏着"不对等解除权"的高风险**。

**教训**：**启发式过滤会漏，而且漏得无声无息**。补救办法不是"把词表写全"（永远写不全），而是：

1. 词表覆盖同义表达，且定期用真实合同回归
2. 过滤结果是 `not_applicable` 而不是消失——保留可追溯
3. 接受"过滤会漏"这个前提，在文档里写明

---

### 决策 9：同一风险标记 merged

**背景**：10 个规则并行跑，同一条款可能被多个规则指向同一个问题。

**实测**：坑合同的第十一条，"不对等解除权"被 `liability` 和 `termination` 各报一次，等级一个 medium 一个 high。

**决策**：`merge_key = (clause_id, risk_fingerprint)`，重复的标 `merged`。

**注意**：
- 不删除，只标 `merged`——**原始模型输出全部保留**
- 报告和结果页只展示等级最高的那条
- 数据库里的 `supported` 计数包含 merged

**为什么不直接去重**：如果以后规则判定调整，需要回溯"当时到底几个规则认为有问题"。删了就查不到了。

---

### 决策 10：任务持久化 + 断点续跑

**背景**：一次审查要 40+ 次模型调用，几十秒到几分钟。进程中途挂掉很常见。

**决策**：

- 任务状态落库（`queued` → `running` → `completed`）
- 每个单元单独事务提交
- worker 启动时把遗留的 `running` 任务重置为 `queued`
- 已 `done` 的单元不重复处理（靠 `item_key` 唯一约束）

**验证**：跑到一半 kill worker，重启后继续，`llm_logs` 里已完成单元的调用次数没有增加。

**代价**：每单元一次事务提交，SQLite 的写性能有影响。但在 44 个单元的规模下可以忽略。

## 四、关键流程

### 依据校验的四层

```
模型返回 evidence_ids = ["a3f2...", "b91c..."]
          │
     第1层：是否是本次候选？
          │  否 → 丢弃
          ▼
     第2层：ID 存在于知识库？
          │  否 → 丢弃（防伪造）
          ▼
     第3层：从数据库读原文（不用模型给的引文）
          │
          ▼
     第4层：有效依据数 > 0？
          │  否 → 降级 insufficient
          ▼
        supported
```

每次校验都打日志：`event=evidence_validation`，含 `candidate_ids`、`model_evidence_ids`、`validation_trace`、最终状态。

**为什么日志要这么细**：出现过的问题——"模型返回空 evidence_ids 还是校验器拒绝了"，只看结果无法区分。日志里记了 `discarded_evidence_ids=[]`，才能确定是模型没给，不是被拒。

### 检查计划生成

```
输入：12 个父条款 + 10 个规则
  │
  ├─ 每个条款 × 每个规则
  │     ├─ 关键词命中 ≥ min_hits → 生成条款级单元
  │     └─ 否则 → not_applicable（不调模型）
  │
  └─ 每个缺失规则 → 生成 1 个合同级单元
```

产出：120 个候选 → 44 个实际调用。

## 五、已知限制

诚实清单，不是"以后会做"的委婉说法。

### 1. 检索不通语义

BM25 只看词面。同义表达（"延期" vs "迟延"、"解约" vs "解除"）召不回来。

**影响**：某些相关法条进不了候选集，模型就无从引用，结果降级为 `insufficient`。

**缓解**：查询时补充固定词（`违约金`规则会额外检索"违约责任"）。

**彻底解决**：需要向量检索，二期。

### 2. 模型判定有波动

同一条款、同样候选，两次运行可能一次判 `supported`、一次判 `insufficient`。

实测：合同 A 第十二条（争议解决），坑合同版判 `supported`，干净合同版判 `insufficient`，两边候选完全相同。

**原因**：LLM 输出不是完全确定性的，`temperature=0` 也只能降低概率不能消除。

**缓解**：记录每次调用的模型名、提示词版本、输入摘要（`input_digest`），出问题能回溯。

**不打算解决**：多次采样取多数会让成本翻三倍。在"辅助工具"的定位下，这个波动可以接受——**用户是法务，他会自己判断**。

### 3. 单机部署

SQLite + 单 worker，不支持多实例。SQLite 同时只允许一个写事务；需要多 worker 写并发时应迁移 PostgreSQL。

**影响**：并发审查性能受限；多租户需要改造。

### 4. 知识库覆盖不足

目前 26 条法规块（民法典合同编节选为主）。

**影响**：很多风险能识别但找不到依据，判 `insufficient`。

**这不是缺陷，是当前数据状态**——宁可判"依据不足"，也不硬凑一条不相关的法条。

### 5. 需求变更检测不到

系统只检查"合同里写了什么"，不检查"和要求相比少了什么"。

比如用户上传了需求清单，系统不会比对"合同里缺了哪项需求"。

---

## 六、如果继续做

按价值排序：

| 优先级 | 做什么 | 为什么 |
|---|---|---|
| 1 | 向量检索（BM25 + 向量混合） | 直接提升召回，减少 insufficient |
| 2 | 人工复核工作流 | 表结构已留好（`human_result` / `decision`），缺 UI |
| 3 | 补齐知识库 | 数据活，见效快 |
| 4 | 合同级缺失规则完成 | 已有 5 个，验证不充分 |
| 5 | 多租户 + 多实例 | 需要换 PostgreSQL，是产品阶段的事 |

## 七、被否决的方案

记录一下当时考虑过但没做的，避免以后重新讨论。

**用 LangChain / LangGraph 编排**

评估后否决。这个项目的流程是固定的三步，引入编排框架只增加抽象层。**流程会变的项目才需要编排**，这里不会变。

**上传时异步解析**

考虑过上传后丢队列解析。否决理由：解析是纯本地计算，几秒完成，用户等得起。异步化反而增加"解析中"这个中间状态的复杂度。

**报告用 JSON 而不是 Markdown**

JSON 结构化更好解析，但用户要读。Markdown 能直接渲染、能下载、能粘贴进任何编辑器。如果以后要做机器消费，再加一个 JSON 接口。

**多租户从第一版就做**

否决。一个人演示的项目做多租户，等于凭空造一个没人用的功能。**它会在需要时出现，不是现在**。

## SQLite 多进程并发与事务边界

API 与 worker 是独立进程，共用 SQLite。正式库原本已是 WAL，WAL 不是本次修复点。此次根因判断为“锁等待超时缺失 + 事务持锁时间过长”，基于现象推断，未做对照实验；原连接已有 5 秒等待，这里的“缺失”指缺少适合当前并发负载的等待配置。真正生效的修复是 busy_timeout 从 5000 调整为 30000，以及收紧事务边界。

每个连接设置 busy_timeout=30000、synchronous=NORMAL，并确认 journal_mode=WAL。WAL 允许读事务与写事务并行，仍然只允许一个写者。NORMAL 降低同步开销，突然断电可能损失最近已提交事务，因此仍需备份。恢复验收期间健康接口与 `/tickets` 各 142 次检测全部返回 200，这是修复后可用性的有效证据，但不能替代根因对照实验。

领取任务使用 BEGIN IMMEDIATE 短事务，领取后立即提交。读取执行快照和检查点后关闭会话，再执行检索、模型 HTTP 请求和退避等待；LLM 请求前的日志预记及请求后的用量记录各自独立提交。结果和去重合并在一个短事务内提交，进度随后在另一个短事务中重算。任务完成与关联工单状态回写使用短事务。所有会话使用上下文管理器，异常自动回滚和关闭。进度可能短暂落后于已保存结果，启动恢复时按已提交单元重算，不能因此重新调用已完成单元。

不要在数据库事务内做模型请求、文件 IO 或等待。WAL/SHM 与数据库必须同目录且目录可写，部署在同一主机文件系统；WAL 不适用于跨主机共享网络文件系统。SQLITE_BUSY 表示锁争用，SQLITE_CANTOPEN（unable to open database file）还可能涉及目录权限、挂载或辅助文件访问失败，不能只通过延长超时掩盖。

`scripts/db_concurrency_check.py` 默认在独立进程逐秒短写 30 秒，同时每 500ms 检测 readiness；任务模式全程记录健康状态、延时、103 个已完成项是否重复调用及模型调用增量。503、其他非 200 和网络超时均判失败。正式库验证不得删除数据库、WAL/SHM 或已有审查结果。


## 立场识别与人工确认

立场识别是上传入口的推荐功能，不是权限判断，也不替用户作出审查立场决定。`party_parser.py` 仅检查全文前 30 行，识别甲乙方标签及委托方/受托方等写法；裸“卖方/买方”按甲/乙展示，最终仍需用户确认。名称遇首个标点结束，只接受 2–50 字；无结果或同侧冲突时返回 null。

用户可在 `PATCH /auth/me` 设置可空组织名（律所可填写本次委托人），字段由当前登录用户 ID 定位，禁止通过请求修改他人或角色。迁移仅添加可空 users.org_name，可重复执行，不重建原表。认证每次读取最新组织信息，JWT 不缓存组织名。

组织匹配使用 Unicode NFKC、去空白和标点后双向包含比较；仅恰好一方匹配时推荐。双方都匹配或都不匹配均返回 null，避免共同公司简称造成误选。单一短名称仍可能误匹配，推荐永远不能替代确认。

Vue 上传流程：选择文件 → 调用无状态 `/parse/preview` → 展示双方名称和推荐 → 用户确认或改选 → `POST /contracts` 发送 party_stance 入库。更换文件会清除旧识别及选择。无匹配时不默认甲方，未选择不能提交；预览错误不进入入库。原 stance 表单参数兼容保留；两个参数冲突返回 422。上传响应也携带识别信息，但不覆盖用户已经确认的立场。现有审查、工单权限和 worker 规则不变。

结果页使用 contracts.title，工单由该标题生成“ · 条款审查”，标题包含已支持文件扩展名时去掉扩展名；不借机修改历史任务快照。

## 按条款合并重复风险，避免事务内二次方扫描

`signature()` 和 winner 排序保持原样（high > medium > low，同级 termination 优先，再按 item_key 稳定排序）。每次提交结果时只调用 `merge_clause_items(session, task_id, clause_id)`，查询同时限制任务和条款；少于两条即返回。合同级缺失单元不参与条款风险合并。所有目标状态先在内存计算，再比较实际内容，仅改变需要合并的行和 winner 的 merged_from；已经达到目标状态的行不重新赋值，原始模型输出保留。

旧实现每个单元都扫描该任务的全部 supported/merged，并反复清除、重建合并元数据；随着 n 个单元提交，累计工作量为 O(n²)，在100+单元中会延长事务持锁时间，是“看似正确但性能差”的典型例子。新实现每次处理同一条款的 m 个候选，当前规则数限制 m 至多10，累计约 O(nm)，不再随整个任务的已完成项数增长。兼容的 merge_task_items 只在任务全部完成后做一次全任务校正，或者由旧数据修复显式调用，不走每单元热路径。

注意区分 ORM dirty、实际 UPDATE、序列化和扫描开销。旧实现的反复赋值会增加 dirty 检查，但 SQLAlchemy 可以跳过最终值相同的 UPDATE，因此“所有脏行都写库”不能作为未经测量的结论。`scripts/merge_perf_check.py` 保留旧实现，使用临时数据库对比120项（12条款×10规则），每10项合并一次，记录每次耗时、dirty和实际UPDATE行数；新版总耗时包含末尾一次校正，不通过附加sleep或增加旧版工作量制造加速比。性能验收是否达到10倍，以输出实测为准。

worker 的 unit_committed 日志包含 committed_at、merge_ms（合并查询、计算与flush）和 checkpoint_ms（结果事务及独立进度事务），便于区分模型响应波动与数据库提交耗时。验收同时每500ms检查readiness；无503能证明该次运行的可用性，不能单凭一次成功运行确定历史503的唯一根因。
